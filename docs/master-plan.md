## A. البنية الحالية (Current Architecture)

| الطبقة | ما هو موجود |
|---|---|
| الواجهة | Next.js 16 (App Router) + React 19 + TypeScript، عربي أولاً مع إنجليزي، Server Actions |
| البيانات | Supabase (Postgres 17) — 89 ترحيلاً، 169 جدولاً، كلها بـ RLS |
| الصلاحيات | RLS + دوال `security definer` تتحقق من المستدعي بنفسها؛ الواجهة لا تقرر شيئاً |
| الاختبارات | 912 اختبار قواعد عمل على Postgres حقيقي + اختبار مزوّد الذكاء الاصطناعي على stub |
| الإنتاج | Supabase `techmood` (فرانكفورت، مجاني) + Vercel `techmoodtech.vercel.app` |
| المهام المجدولة | pg_cron: انتهاء الحجوزات، إغلاق الجلسات، التذكيرات، طلبات المنتور بلا ردّ |
| الذكاء الاصطناعي | طبقة مساعد تقرأ كصاحب الحساب، تقترح ولا تنفّذ؛ غير موصولة بمفتاح بعد |

الأدوار الموجودة: طالب، مستفيد إرشاد (mentee)، فريلانسر، عميل، منتور، قائد فريق، مؤسس، مؤسسة، إدارة.

## B. البنية المقترحة (Recommended Architecture)

**لا إعادة بناء.** البنية الحالية هي نفسها ما تطلبه الوثيقة: منطق العمل في قاعدة البيانات، حالات بـ enums،
سجل مالي (ledger) لا رصيد مخزّن، سجل تدقيق، وأدوار بصلاحيات. التوسعات المقترحة تُبنى فوقها:

1. **طبقة «السوق» الموحدة**: الجلسات، المشاريع، الخدمات، الوظائف كلها «طلب» (order) يمر بنفس دورة
   الدفع اليدوي → التحقق → التسليم → الإفراج — بدل أن يكون لكل قسم دورته الخاصة.
2. **طبقة اجتماعية** (متابعة، إعجاب، تعليق، مشاهدات، مشاركة) عامة على أي «كيان» (مشروع، كورس، مسار، شهادة)
   بجدول تفاعلات واحد، لا جدول لكل نوع.
3. **PWA + إشعارات الجهاز** فوق محرك الإشعارات الموجود (0065) — قناة توصيل جديدة، لا نظام إشعارات ثانٍ.
4. **المحتوى من المنتورز** يستخدم نفس جداول الأكاديمية (paths/courses/lessons) مع حقل «المنشئ» ودورة مراجعة.

## F. آلات الحالة (State Machines)

**الحجز (موجود، مع إضافة فترة التقييم):**
`draft → payment_pending → payment_submitted → payment_verified → mentor_pending → confirmed → completed → [evaluation_period 7 أيام] → closed`
بدائل: `payment_pending → expired` · `payment_submitted → rejected` · `mentor_pending → rejected (أو تلقائياً بعد المهلة)` · أي حالة قبل الجلسة → `cancelled → refunded`

**طلب المنتور (موجود):** `pending_review → needs_more_info → approved | rejected` — الرفض يُبقي الحساب طالباً.

**إدراج مشروع للبيع (جديد):** `draft → pending_review → verified(listed) → reserved → sold (يبقى listed إن كان الترخيص يسمح بالبيع المتكرر)` · بديل: `rejected` (يُحذف ويُسجَّل أثره على سمعة البائع) · `withdrawn`

**طلب شراء/خدمة (جديد، نفس دورة الجلسة):** `created → payment_pending → payment_verified → delivered (كشف الرابط المخفي) → completed → released` · بدائل: `rejected → refund_pending → refunded`

**كورس/مسار منتور (جديد):** `draft → submitted → admin_review → approved → published` · بدائل: `changes_requested`، `rejected`

**الاسترداد:** `refund_pending → refunded (مع إثبات تحويل وحساب المستلم)`

**السحب (موجود):** `requested → processing → completed` مع مرجع التحويل وإثباته.

## G. خارطة التنفيذ (MVP أولاً)

### المرحلة 1 — يُنفَّذ الآن (يكمل ما هو مبني)
1. ✅ **قرارات التسعير الجديدة** (0090) — مستويات المنتور بحدود 10–150$ وعمولة 30% ثابتة (انظر «قرار مطلوب»)؛ عمولة بيع المشاريع 15%.
2. ✅ **إلغاء المحادثات المالية** (0091–0092) — إغلاق محادثات الحجز والتفاوض؛ قناة TechMood الرسمية (من طرف واحد).
3. ✅ **المنتور المتقدّم** (0093) — يدخل المنصة ويستخدمها وطلبه «قيد المراجعة» ظاهر دائماً؛ الحقول الأساسية فقط إلزامية؛ الرفض يعيده طالباً.
4. ✅ **الجلسة والتقييم** (0094–0095) — المنتور يرى الطلب وملف الطالب بعد تأكيد الدفع، ويفتح تسليماته ومشاريعه بعد القبول، ويقيّم حتى أسبوع بعد الجلسة؛ التقييم إلزامي إن طلب الطالب مراجعة؛ الطالب يأخذ XP عند تأكيد الحجز.
5. ✅ **تسليم المشاريع** (0096) — رابط المشروع إلزامي، رابط شرح يوتيوب اختياري (اليوم: لينكدإن ويوتيوب إلزاميان ⚠️).
6. ✅ **الفاتورة** (0097) — لكل دفعة، في سجل المحفظة، قابلة للطباعة PDF؛ وتسجيل الحساب الذي دُفع منه للإرجاع.
7. ✅ **سوق المشاريع المضبوط** (0098–0099) — مراجعة الإدارة قبل الظهور، رابط مخفي يُكشف بعد التحقق من الدفع، ديمو ومعاينة، بيع متكرر، خصم/عرض، عدد المبيعات، شارة «تم التحقق».
8. ✅ **PWA** — أيقونة على الشاشة الرئيسية، اقتراح التثبيت (غير مزعج)، و«تثبيت التطبيق» في الإعدادات.
9. ✅ **إشعارات الجهاز** (0100) — تفعيل من الإعدادات، تذكير يومي، أحداث، رسائل؛ الإدارة ترسل لمستخدم أو لدور أو للكل (البث موجود ✅ ويُضاف التوصيل للجهاز).
10. ✅ **لوحة كل دور** — المنتور: الحجوزات والتقويم أولاً؛ الطالب: الأكاديمية؛ وشرح «أين أنت وماذا تفعل» في كل صفحة.
11. ✅ **دليل التقييمات والترقيات** (0101) — صفحة تشرح المعايير ونظام المستويات، واستبيان ترقية الرتبة يراجعه المدير.

### إعادة الهيكلة إلى MVP (0103–0106)
1. ✅ **مفتاح النطاق** (0103) — الشركات الناشئة والحاضنة والشركات والفريلانس والوظائف مخفية لا محذوفة؛ الأدوار: طالب، منتور، Mentee.
2. ✅ **الحجز** (0104) — قبول الدفعة يؤكّد الجلسة مباشرة، ورفضها يحرّر الموعد؛ المنتور يعتذر قبل الموعد بسبب ويُعاد المبلغ؛ رابط الاجتماع (Zoom/Meet) خاص بالحجز ويظهر للطالب قبل الموعد بعشر دقائق؛ الحضور يُسجَّل (انعقدت / غاب الطالب / غاب المنتور) ولا يُغلق تلقائياً.
3. ✅ **الدفع** (0105) — بنك فلسطين وحده للدفع (بياناته في Admin → Finance → Accounts لا في الكود)؛ الاستلام على حساب بنكي أو PalPay أو Jawwal Pay فقط.
4. ✅ **المتابعة والإعجاب** (0106) — متابعة الأعضاء والمنتورز، والإعجاب بمشاريع الآخرين؛ الأعداد عامة ومن تابع من خاص.

## H. المخاطر والدين التقني

- **الدفع يدوي بالكامل** — كل عملية تحتاج مراجعة بشرية؛ مقبول للإطلاق، يحتاج بوابة دفع عند النمو.
- **Google Login غير مفعّل** — يحتاج إعداد OAuth في Google Cloud.
- **لا بريد مرسَل من المنصة** — صندوق الإرسال جاهز، مزوّد البريد غير موصول (بريد Supabase المجاني محدود جداً للتأكيد فقط).
- **مفتاح الذكاء الاصطناعي غير مضبوط** — المساعد والتحليل الذكي معطّلان بوضوح حتى يُضاف.
- **اقتراحات أداء** من Supabase (فهارس مفاتيح أجنبية، سياسات متداخلة) — تُعالج عند وجود حمل حقيقي.
- **ملكية المشاريع المباعة** — البيع المتكرر يحتاج نوع ترخيص واضح لكل بيع لتجنب نزاعات.
- **الألقاب والنقاط** — يجب ربطها بأحداث حقيقية مع حدود يومية حتى لا تُستغل بالإعجابات المتكررة.
